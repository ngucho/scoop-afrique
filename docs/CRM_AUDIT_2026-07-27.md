# Audit complet du CRM Scoop Afrique

Date : 27 juillet 2026  
Périmètre : `apps/crm`, API CRM de `apps/backend`, schéma et migrations PostgreSQL/Supabase, base Supabase connectée.  
Nature : inventaire et diagnostic uniquement. Aucune règle métier ni donnée n'a été modifiée.

## 1. Conclusion exécutive

Le CRM couvre déjà l'essentiel du cycle commercial et opérationnel :

- demandes de devis ;
- contacts et organisations ;
- devis avec PDF, envoi et signature électronique ;
- conversion devis → projet ;
- projets, contacts projet, tâches, livrables et métriques ;
- factures, paiements et reçus PDF ;
- contrats ;
- relances ;
- dépenses projet, trésorerie, rapports et bilan exportable ;
- paramètres de paiement, entreprise et relances ;
- journal d'activité et RBAC Auth0.

Le socle fonctionnel est large, mais le cycle de vie des données n'est pas cohérent. L'action affichée comme « supprimer » est en réalité un archivage individuel. Archiver un projet ne traite pas ses éléments associés et fausse ensuite certaines vues et certains indicateurs.

Constat confirmé dans la base réelle :

- 45 projets au total ;
- 6 projets archivés ;
- 2 devis encore actifs liés à ces projets archivés ;
- 1 facture encore active liée à un projet archivé.

La bonne évolution n'est pas de supprimer automatiquement tous les documents. Les pièces financières et contractuelles doivent être conservées. Il faut introduire une politique de cycle de vie explicite, transactionnelle et traçable.

Deux sujets de sécurité doivent être traités avant les améliorations UX :

1. Le backend lit le contenu des JWT Auth0 sans vérifier leur signature cryptographique.
2. Le rôle dérivé de `read:crm` est autorisé à appeler de nombreuses routes d'écriture.

## 6. Archivage et suppression : fonctionnement actuel

### 6.1 Ce que fait réellement l'action projet

`DELETE /projects/:id` appelle `archiveProject()`, qui exécute uniquement :

```text
crm_projects.is_archived = true
```

Puis une activité `project / archived` est créée. Aucun devis, facture, contrat, paiement, reçu, rappel, mouvement de trésorerie, tâche, livrable ou dépense n'est modifié.

La raison saisie dans la boîte de dialogue d'archivage n'est pas envoyée au backend. Elle apparaît uniquement dans le toast local puis est perdue.

### 6.2 Effet actuel par type d'élément

| Élément lié | Lors de l'archivage projet | Conséquence |
|---|---|---|
| Devis | reste actif | visible dans Devis et compté dans certains pipelines |
| Facture | reste active | visible, encaissable et comptée dans certains KPI |
| Paiement | reste actif | recette conservée, ce qui est comptablement souhaitable |
| Reçu | reste générable | lien avec la facture conservé |
| Contrat | reste actif | visible indépendamment du projet |
| Relance | reste active/programmée | peut continuer à être envoyée |
| Tâche | reste en base | accessible par endpoint imbriqué |
| Livrable | reste en base | accessible par endpoint imbriqué |
| Dépense | reste en base | continue à peser dans les rapports |
| Trésorerie | reste active | continue à peser dans les rapports |
| Contacts projet | reste en base | relation conservée |

### 6.3 Ce que ferait une vraie suppression SQL du projet

Les contraintes actuelles appliqueraient :

- suppression en cascade : tâches, livrables, métriques via livrables, dépenses, contacts projet ;
- conservation avec `project_id = NULL` : devis, factures, contrats, relances, trésorerie ;
- conservation des paiements et reçus car les factures restent présentes.

Une suppression SQL ne répondrait donc pas non plus au besoin métier. Elle détruirait des éléments opérationnels, détacherait les pièces financières et ferait perdre la cohérence du dossier.

## 7. Politique cible recommandée

### 7.1 Principe

Ne jamais supprimer automatiquement une pièce financière ou contractuelle ayant une valeur légale ou historique :

- facture émise ;
- paiement ;
- reçu ;
- devis envoyé ou accepté ;
- contrat envoyé ou signé ;
- dépense et justificatif comptable ;
- mouvement de trésorerie.

### 7.2 Action « Archiver le dossier projet »

L'action doit afficher un aperçu d'impact :

```text
Archiver le projet PRJ-…
  1 devis actif
  2 factures dont 1 payée
  1 contrat signé
  4 tâches ouvertes
  2 relances programmées
```

Puis appliquer en une transaction :

1. archiver le projet avec `archived_at`, `archived_by`, `archive_reason` ;
2. archiver automatiquement les brouillons de devis, factures et contrats ;
3. conserver les documents envoyés, acceptés, signés, payés ou annulés dans un espace « Documents historiques » ;
4. annuler les relances futures non envoyées ;
5. figer ou annuler les tâches ouvertes ;
6. masquer tâches et livrables des vues opérationnelles normales ;
7. conserver dépenses, paiements, reçus et trésorerie dans les rapports ;
8. inscrire chaque effet dans un journal d'audit ;
9. permettre la restauration uniquement des éléments archivés par cette action.

### 7.3 Suppression définitive

Réserver la suppression définitive aux brouillons sans dépendances, avec :

- contrôle administrateur ;
- saisie obligatoire d'une raison ;
- double confirmation ;
- aperçu des dépendances ;
- transaction ;
- journal d'audit ;
- délai ou corbeille avant purge.

## 8. Constats classés par gravité

### Critique

#### C1 — JWT Auth0 non vérifié cryptographiquement

Le backend décode le JWT puis vérifie seulement `iss`, `aud` et `exp`. Il n'utilise ni la signature ni les clés JWKS Auth0. Un jeton forgé peut donc théoriquement déclarer des permissions CRM et atteindre l'API.

Fichiers :

- `apps/backend/src/lib/auth0.ts`
- `apps/backend/src/lib/auth.ts`

Remède : utiliser `jose`, `createRemoteJWKSet()` et `jwtVerify()` avec issuer et audience, puis tester les jetons invalides, expirés et signés avec une mauvaise clé.

#### C2 — Le droit de lecture donne de nombreux droits d'écriture

`read:crm` produit le rôle `editor`. La majorité des groupes de routes acceptent `editor`, `manager`, `admin` pour les lectures et les mutations. Un utilisateur ayant seulement le droit de lecture peut notamment créer ou modifier contacts, organisations, devis, factures, paiements, relances, tâches, livrables, dépenses et paramètres.

Remède : contrôler les permissions exactes par méthode :

- GET : `read:crm` ;
- POST/PATCH métier : `write:crm` ;
- archives, restaurations, paramètres sensibles et suppressions : `manage:crm`.

### Élevé

#### H1 — Archivage projet non propagé et incohérence avérée

La base contient actuellement 2 devis et 1 facture actifs rattachés à des projets archivés.

#### H2 — Les indicateurs n'appliquent pas tous les mêmes filtres

Certaines requêtes filtrent `is_archived = false`, d'autres non :

- dashboard : pipeline devis, projets actifs/en retard et factures impayées non filtrés ;
- rapports : pipeline et conversion non filtrés ;
- dépenses et trésorerie d'un projet archivé restent comptées.

#### H3 — « Envoyé » ne signifie pas livré

Les endpoints devis/facture passent d'abord le statut à `sent`, lancent email/WhatsApp en tâche asynchrone, absorbent les erreurs et répondent immédiatement avec succès. Si Resend/Twilio n'est pas configuré ou échoue, l'UI affiche tout de même « envoyé ».

Remède : journal de livraison avec états `queued`, `sent`, `delivered`, `failed`, retries et message utilisateur honnête.

#### H4 — Aucun test CRM

Les 20 tests existants concernent d'autres domaines. Aucun test ne couvre :

- archivage/restauration ;
- cycle devis → projet → facture → paiement ;
- calcul des totaux ;
- permissions ;
- notifications ;
- rapports ;
- signatures ;
- transactions.

#### H5 — Absence de transactions sur les opérations multi-étapes

Exemples :

- création paiement puis recalcul facture puis activité ;
- conversion devis puis création projet ;
- création projet puis contact principal puis demande convertie ;
- futur archivage en cascade.

Une erreur intermédiaire peut laisser une base partiellement mise à jour.

#### H6 — Journal d'activité incomplet

Organisations, livrables, métriques, dépenses, relances, prestations, paramètres et trésorerie n'écrivent pas systématiquement dans le journal. Les suppressions de tâches et mouvements ne sont pas auditables.

### Moyen

#### M1 — Règles de relance « automatiques » non exécutées

Le CRM permet leur CRUD, mais aucun cron, worker ou service ne les consomme.

#### M2 — Reçu non envoyé lors du paiement

La notification de paiement est appelée sans buffer de reçu ; l'email avec reçu n'est donc jamais envoyé par ce flux.

#### M3 — URL PDF persistée mais expirant après 7 jours

Le stockage est privé et `pdf_url` reçoit une URL signée d'une durée de 7 jours. Les liens historiques de la finance projet deviennent obsolètes. Il faut stocker le chemin objet, puis signer à la demande.

#### M4 — Recherche et notifications globales factices

Le bouton « Rechercher… ⌘K » et la cloche n'ont aucun gestionnaire ni destination.

#### M5 — Pagination absente

Les pages chargent 50 ou 100 éléments au maximum sans navigation vers la suite. Le CRM possède déjà 222 mouvements de trésorerie, donc le problème est concret.

#### M6 — Couverture CRUD inégale

- organisations : pas d'archive/suppression ;
- dépenses : création et liste seulement ;
- livrables : pas de suppression ;
- paiements : pas d'annulation/suppression contrôlée ;
- tâches et trésorerie : suppression définitive ;
- demandes de devis : archivage et suppression définitive coexistent sans politique globale.

#### M7 — UX d'administration fragile

- boîtes natives `prompt()` et `confirm()` ;
- raison d'archive perdue ;
- UUID bruts dans le fil d'Ariane ;
- contrat édité en JSON ;
- justificatifs saisis comme URL ;
- création projet visible pour des rôles qui recevront ensuite un 403 ;
- sidebar Trésorerie visible avant redirection pour les rôles non autorisés.

#### M8 — Complexité de fichiers

- `SettingsClient.tsx` : 1 075 lignes ;
- `TreasuryClient.tsx` : 563 lignes ;
- `RemindersClient.tsx` : 495 lignes ;
- dashboard : 482 lignes.

Les types `Record<string, unknown>` et conversions manuelles sont omniprésents, ce qui masque les invariants métier.

#### M9 — Performance et index

Le dossier projet charge les paiements facture par facture, soit un motif N+1. Les advisors Supabase signalent aussi plusieurs clés étrangères CRM sans index couvrant, notamment :

- `crm_reminders.project_id` ;
- `crm_reminders.invoice_id` ;
- `crm_treasury_movements.project_id` ;
- `crm_projects.organization_id` ;
- `crm_projects.devis_id` ;
- `crm_invoices.devis_id` ;
- `crm_contracts.contact_id` et `devis_id`.

Référence : https://supabase.com/docs/guides/database/database-linter?lint=0001_unindexed_foreign_keys

#### M10 — Migrations de bootstrap dangereuses mais base actuelle saine

Les migrations historiques `0014`, `0016` et `0017` contiennent des politiques `FOR ALL TO public USING (true)`. La base connectée ne les possède plus et n'accorde des privilèges CRM qu'à `service_role`.

Le risque concerne la création d'un nouvel environnement ou un bootstrap incomplet. Il faut supprimer ou neutraliser ces politiques historiques dans le chemin de provisioning vérifié.

## 11. Décisions métier à valider avant implémentation

1. Une facture brouillon doit-elle être archivée automatiquement avec le projet ?
2. Une facture envoyée mais impayée doit-elle rester dans « Factures actives » ou passer dans « Documents historiques à recouvrer » ?
3. Une facture payée doit-elle rester visible dans les rapports même si le projet est archivé ? Recommandation : oui.
4. Les devis envoyés/acceptés doivent-ils rester visibles hors du projet ? Recommandation : oui, dans l'historique.
5. Les tâches ouvertes doivent-elles être annulées, figées ou archivées ?
6. Les relances programmées doivent-elles être annulées automatiquement ? Recommandation : oui, avec confirmation.
7. Quelle durée de conservation appliquer aux pièces financières et contrats ?
8. Qui peut restaurer un dossier : manager ou administrateur ?
9. Faut-il une corbeille avec purge différée, par exemple 30 jours, pour les seuls brouillons ?
